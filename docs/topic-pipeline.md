# Topic-to-Briefing Pipeline

How a user's topic becomes a news briefing, from input to output.

## Overview

```
User topics → Resolve → Fetch articles → LLM assembly → Briefing JSON
```

All stages run in parallel across topics. Total time: ~15-20s for 4 topics.

---

## Stage 1: Topic Resolution

**File:** `src/lib/query-planner.ts` → `resolveTopics()`

Each topic goes through three checks in order. First match wins.

### Path A: Curated Topic Match

`findCuratedTopic()` in `topic-engine.ts` does a case-insensitive match against 42 pre-defined topics. Two passes:

1. **Exact match** on `displayName` (e.g., "NBA" → `nba`)
2. **Partial match** — either string contains the other (e.g., "Politics" → `us_politics` because "us politics" contains "politics")

If matched, the curated config is converted to `QueryInstruction`s:
- Curated `queryStrategy: "articles"` → `{ type: "articles", query: keywordQuery }`
- Curated `queryStrategy: "both"` → `{ type: "both", query: keywordQuery, vectorQuery: vectorPrompt }`

No LLM call needed.

### Path B: Cached Query Plan

Redis key: `queryplan:topic:{lowercase topic name}`, 24-hour TTL.

If a plan was previously generated by the LLM for this topic, it's reused directly.

### Path C: LLM Query Planner

All remaining topics are sent to GPT-5-nano in a **single batch call**. The LLM returns a `QueryPlan` for each topic with one or more `QueryInstruction`s.

The LLM decides:
- **Search type** for each query: `"articles"`, `"vector"`, or `"both"`
- **Query string** optimized for search (not necessarily the user's exact wording)
- **Whether to split** compound topics (e.g., "AI and Tech" → two separate queries)

Each plan is individually cached in Redis (24h TTL).

**Fallback:** If LLM fails after one retry, each topic gets a basic `{ type: "articles", query: topicName }`.

## Stage 2: Article Fetching

**File:** `src/lib/briefing-generator.ts` → `fetchQueryArticles()` + `executeQuery()`

Each `QueryInstruction` is executed independently (with caching). The behavior depends on the instruction's `type`.

### Type: `"articles"` — Cascade Fallback

Three steps, stops at the first that returns >= 3 articles:

| Step | Endpoint | Source Filter | Date Range | Other Filters |
|------|----------|---------------|------------|---------------|
| 1 | `/v1/articles/all` | `sourceGroup: ["top100"]` | 3 days | `excludeLabel: [Non-news, Opinion, Paid News]`, `showReprints: false`, `sortBy: relevance`, `language: en`, `medium: Article` |
| 2 | `/v1/articles/all` | None (all sources) | 7 days | Same label/reprint/language/medium filters |
| 3 | `/v1/vector/news/all` | None | None | Semantic search, `size: 10` only |

Step 1 is the highest quality (top 100 curated sources, recent, no junk). Each subsequent step relaxes filters to find content for niche topics.

### Type: `"vector"` — Semantic Search Only

Direct call to `POST /v1/vector/news/all` with the query as the prompt. No quality filtering. Used rarely — only when the LLM planner determines keyword search would fail.

### Type: `"both"` — Parallel Merge

Runs Step 1 of the articles cascade AND vector search simultaneously. Results are merged, deduplicated by URL (articles/all version preferred since it has richer metadata: labels, categories, etc.).

Used for niche topics that benefit from both keyword and semantic matching.

### Caching

Each query result is cached in Redis for 6 hours.

Key: `perigon:q:{hash of type:query}` — keyed by the query string, not the topic name. This means if "AI and Tech" splits into a query for "artificial intelligence AI" and a standalone "Artificial Intelligence" topic uses the same query string, they share the cache.

---

## Stage 3: Article Merging (Multi-Query Topics)

When a topic has multiple queries (e.g., "AI and Tech" split into two), results are merged:

1. **Interleave** — alternates articles from each query (1st from query A, 1st from query B, 2nd from A, 2nd from B...) for balanced coverage
2. **Deduplicate** by URL — keeps the first occurrence
3. **Take top 10** articles
4. **Prepare** for LLM — each article becomes `{ title, source, date, summary, url }`

---

## Stage 4: LLM Briefing Assembly

**File:** `src/lib/briefing-generator.ts` → `assembleWithLLM()`

The prepared articles are sent to GPT-5-nano with a system prompt (`src/lib/prompts.ts`) that instructs it to:

- Write a 2-3 sentence summary of the topic area
- Create 3-6 distinct story cards (depending on briefing length setting)
- Each card: headline, bullet points, source name, URL, date
- Use only the provided article URLs (no fabrication)
- Synthesize multiple articles about the same event into one story
- Weave sub-topics together rather than separating them

The LLM retries once on failure. If both attempts fail, a fallback briefing is returned with just the topic name and no stories.

All topic assemblies run in **parallel** via `Promise.all`.

---

## Summary of Search Quality Tiers

From highest to lowest quality:

| Tier | Source | Filtering | When Used |
|------|--------|-----------|-----------|
| Articles (top100, 3d) | `/v1/articles/all` | Top 100 sources, no opinion/non-news, deduped, relevance-sorted | Default for all `"articles"` queries |
| Articles (broad, 7d) | `/v1/articles/all` | All sources, no opinion/non-news, deduped, relevance-sorted | Fallback when top100 returns < 3 results |
| Both (merged) | articles + vector | Articles portion filtered; vector portion unfiltered | Niche topics that benefit from semantic expansion |
| Vector only | `/v1/vector/news/all` | No quality filtering | Last resort; abstract/conceptual queries only |

## Perigon API Endpoints Used

| Endpoint | Method | Purpose |
|----------|--------|---------|
| `/v1/articles/all` | GET | Primary article search with full filtering |
| `/v1/vector/news/all` | POST | Semantic search (fallback/supplement) |
| `/v1/all` | GET | Legacy endpoint (used only by `createCustomTopicConfig`) |
