Pipeline Analysis

Query Planner

  • Architecture: Curated topics (4 categories, 40+ configs) skip LLM planning entirely — efficient and consistent.
  • Custom topics: LLM planner generates search queries with type selection (articles/vector/both). Plans cached 24h in Redis.
  • Splitting logic: Compound topics like "AI and Tech" are split into separate queries — good for coverage breadth.
  • Strength: Three-tier search type system (articles → vector → both) is well-designed for varying topic specificity.

Perigon Search Quality

  • Cascade fallback: top100 sources (3d) → any source (7d) → vector search. This is excellent for balancing quality vs coverage.
  • Source filtering: Excludes Non-news, Opinion, Paid News labels. Reprints filtered. English-only, Article medium.
  • Interleaving: Multi-query results are round-robin interleaved then deduped — ensures balanced coverage.

Caching

  • TTL: 6 hours for article results, 24 hours for query plans. Section-level caching available.
  • Recommendation: 6h TTL is reasonable for news. Consider 3-4h for breaking-news-heavy topics (politics, markets).

Error Handling

  • LLM retry: Single retry on parse failure — good basic resilience.
  • Cascade fallback: 3-step article search degradation prevents empty results.
  • Graceful degradation: Failed topics return stub briefing rather than crashing entire request.

Cost Efficiency

  • Model: GPT-5-nano at $0.15/$0.60 per 1M tokens — very cost-effective.
  • Per briefing: ~1 query planner call + 1 assembly call per topic. Cached queries avoid redundant Perigon API hits.
  • Estimated cost: ~$0.001-0.003 per topic section (nano pricing). Full 5-topic briefing ≈ $0.01-0.02.

Key Findings

✅ What Works Well

  • Source quality filtering — top100 sourceGroup + label exclusion produces reliable, reputable sources
  • Curated topic configs — pre-optimized queries for 40+ topics bypass LLM planning, improving speed and consistency
  • Cascade fallback — 3-step degradation ensures coverage even for niche topics
  • Cost efficiency — GPT-5-nano keeps per-briefing costs under $0.02
  • Deduplication — URL-based dedup + reprint filtering prevents repetitive content
  • Parallel execution — all topics fetched and assembled concurrently

❌ What Needs Improvement

  • Date filtering too permissive: 2-month window allows stale content. Consider 7-14 day max for mainstream topics.
  • No URL validation: LLM could hallucinate or mangle URLs. Add runtime URL validation (check HTTP status).
  • Vector search quality: No source quality filtering on vector endpoint — can return low-quality content. Post-filter vector results by known source lists.
  • Missing topic coverage detection: No mechanism to detect if major breaking stories are missing. Consider a "coverage check" step.
  • Section caching unused in main flow: getCachedSection is checked but setCachedSection is never called in briefing-generator.ts. Wire it up to cache assembled sections.
  • No token usage tracking: Usage is logged but not stored. Track in Redis for cost monitoring dashboards.
  • Edge case topics: Very broad ("news") or very niche ("Morgan Stanley wealth management") may produce poor results. Consider pre-validation or user guidance.

Actionable Recommendations

  1. Tighten date filter: Reduce max age to 14 days for broad topics, 30 days for niche. Add per-category TTL config.
  2. Cache assembled sections: Call setCachedSection after successful assembly to avoid redundant LLM calls for the same topic within 6h.
  3. URL health check: Spot-check 1-2 URLs per briefing with HEAD requests. Flag or replace dead links.
  4. Vector post-filtering: Apply source reputation scoring to vector search results before feeding to LLM.
  5. Usage dashboard: Store token counts + Perigon API call counts in Redis. Build a /admin/usage page.
  6. Adaptive cache TTL: 3h for politics/markets, 6h for tech/sports, 12h for niche/lifestyle.
